# PRD — منصة الاختبارات (مدرسة الخيرات للتعليم الأساسي)

## Original Problem Statement
نظام إدارة مدرسي متكامل لمدرسة الخيرات: اختبارات، مشاريع، تقييم سريع، سجلات درجات. مع دعم العام الدراسي (2025/2026 → 2029/2030) وفصلين دراسيين.

## Architecture
- **Backend**: FastAPI + MongoDB (motor) — `/app/backend/server.py`
- **Frontend**: React + TailwindCSS — `/app/frontend/src/`
- **Auth**: JWT
- **LLM**: OpenAI GPT-4o عبر Emergent LLM Key (مولّد بنك الأسئلة)

## Key API Endpoints
### Auth/Settings
- `POST /api/auth/login`
- `GET /api/academic-years`, `PUT /api/academic-years/current`, `PUT /api/academic-years/semester`

### Grade Sessions (الجديد)
- `POST /api/grade-sessions` — إنشاء جلسة (rubric_id + gradebook_id)
- `GET /api/grade-sessions` — قائمة جلسات المعلم
- `GET /api/grade-sessions/{sid}` — تفاصيل + قائمة الطلاب في السجل
- `DELETE /api/grade-sessions/{sid}` — حذف
- `POST /api/grade-sessions/{sid}/release` — إرسال
- `POST /api/grade-sessions/{sid}/reopen` — إعادة فتح
- `PUT /api/grade-sessions/{sid}/participants/{pid}` — مطابقة/تأكيد/رفض
- `DELETE /api/grade-sessions/{sid}/participants/{pid}` — إزالة مشارك
- `GET /api/public/grade-sessions/{code}` — معلومات عامة (للطالب)
- `POST /api/public/grade-sessions/{code}/join` — انضمام طالب
- `GET /api/public/grade-sessions/{code}/state?participant_id=...` — استعلام عن الحالة

## Data Models
- `grade_sessions`: `{id, code, owner_id, rubric_id, rubric_title, gradebook_id, grade, section, column, column_label, semester, status (open|released|closed), participants[], released_at, created_at}`
- `participants[]` item: `{id, joined_name, joined_grade, joined_section, matched_student_id, matched_student_name, match_confidence, confirmed, ignored, joined_at}`
- `rubrics`: `{id, owner_id, year, title, semester, column, criteria[], images[], total_max, created_at, updated_at}`
- `rubric_evaluations`: `{rubric_id, gradebook_id, student_id, scores{cid:val}, total, gb_score}`

### السبب الجذري الحقيقي: فشل صامت في استيراد الطلاب عند وجود مسافة في عنوان العمود (أكتوبر 2026)
- المستخدم كرر الشكوى بعد الإصلاح السابق (الذي عالج فقط تحويل الأرقام العشرية ".0" ولم يكن السبب الكامل). أعاد الوكيل إنتاج المشكلة فعلياً عبر محاكاة متصفح حقيقية (رفع ملف Excel برأس عمود "اسم الطالب" — وهي الصياغة الطبيعية الأكثر شيوعاً) ووجد أن حقل "الاسم" في نافذة تحديد الأعمدة يبقى **غير معيَّن تلقائياً** ("— لا يوجد —")، لأن دالة التطبيع `norm_ar()` المستخدمة في مطابقة عناوين الأعمدة لا تحذف المسافات، فـ"اسم الطالب" (بمسافة) لا تُطابق القيمة المرجعية "اسمالطالب" (بدون مسافة) المكتوبة في الكود. بما أن حقل الاسم إلزامي، هذا كان يُعطّل الاستيراد بالكامل بصمت — وهو ما يفسّر تماماً شكوى المستخدم (لا يوجد أي طالب محفوظ فعلياً، فتفشل كل عمليات البحث برقم مدني ولا تظهر أي أسماء للمعلمين).
- **الإصلاح**: أُضيفت دالة `norm_nospace()` (تُطبّع الحروف العربية ثم تحذف كل المسافات) واستُبدلت بها `norm_ar()` في جميع نقاط مطابقة عناوين الأعمدة (5 مواضع): معاينة/استيراد المعلمين، معاينة/استيراد الطلاب، ودالة `_excel_cells` المستخدمة في نافذة مطابقة المعلمين مع نظام الاحتياط.
- **التحقق**: أعاد الوكيل تكرار نفس سيناريو الاستيراد بعد الإصلاح مباشرة عبر متصفح حقيقي — عمود الاسم أصبح يُكتشف تلقائياً بشكل صحيح، زر التأكيد يُفعَّل، ويتم الاستيراد بنجاح مع ظهور الطلاب في صفحة ولي الأمر وفي "إدخال الدرجات" لكل من المدير وحساب معلم حقيقي (تم تسجيل الدخول فعلياً بحساب معلم من الـ112 معلماً المستوردين). **تم استدعاء `testing_agent` لتأكيد الإصلاح بشكل مستقل (وفق السياسة الإلزامية) — نتيجة الاختبار: 100% (7/7 اختبارات باك-إند جديدة + تحقق واجهة كامل)، بدون أي action items.** ملف الاختبار الجديد: `/app/backend/tests/test_grades_import_space_headers.py`.

### السبب الجذري الثالث والأخير: رموز RTL خفية (\u200f) من ملفات إكسل المدرسة الحقيقية (أغسطس 2026)
- المستخدم رفع ملفه الحقيقي `الارقام المدنيةللطلاب.xlsx` بعد الإصلاحين السابقين وأكد استمرار المشكلة. فحص الملف كشف أن خلايا الأسماء/الأرقام المدنية تحتوي رموز تحكم خفية غير مرئية (`\u200f` RTL mark وما شابه من `\u200b-\u200f`, `\u202a-\u202e`, `\ufeff`) — ناتجة عن تصدير النظام المدرسي الأصلي. السبب: دالة `cell_str()` المشتركة كانت تحتوي على regex تنظيف صحيح، **لكنها لم تكن مستخدَمة فعلياً** في ثلاث دوال `cell()` محلية منفصلة داخل `/students/import` و`/teachers/import/preview` و`/teachers/import/commit` — هذه الدوال المحلية كانت تستخدم `str(v).strip()` فقط (لا يحذف الرموز الخفية)، فتُخزَّن البيانات في القاعدة بالرموز الخفية الملتصقة، فتفشل كل مطابقة لاحقة (بحث ولي الأمر، تسجيل دخول معلم بالرقم المدني).
- **الإصلاح**: استبدال الدوال المحلية الثلاث لاستخدام `cell_str()` الموحدة. كذلك تم تطهير نقاط الإدخال اليدوي (`POST /teachers`, `POST /students`, `PUT /teachers/{id}`, `PUT /students/{sid}`) وتعقيم مدخل البحث العام `GET /parent/results` (مع `re.escape` في fallback الـ regex بدل تركيب نص خام).
- تم تشغيل سكربت تنظيف لمرة واحدة (`/app/backend/migrate_clean_unicode.py`) على القاعدة الحالية (0 سجلات متأثرة — لا بيانات قديمة ملوّثة في القاعدة وقت الإصلاح).
- **التحقق**: اختبار curl مباشر برفع ملف Excel تجريبي يحتوي `\u200f` حول الاسم/الرقم المدني → تأكيد التخزين النظيف والعثور الفوري عبر بحث ولي الأمر. ثم `testing_agent`: 8/8 اختبارات باك-إند ناجحة (`test_grades_unicode_sanitization.py`, iteration_24.json)، بدون أي action items أو مشاكل واجهة.
